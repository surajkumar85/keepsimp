## KeepSimp project rules

Read `docs/design-system.md`, `design-system/tokens.json`, and `docs/phase-one.md` before implementing product UI. The design reference is the persistent authority for future phases.

- Use Next.js App Router, TypeScript strict mode, npm, and the committed lockfile. The app exports static files; browser file processing must stay local. Do not introduce uploads, accounts, paid tools, or server processing without a user request.
- Preserve the requested shadcn preset `b2zSMmeGTw`: Base Nova, Base UI primitives, Tabler icons, Inter body, Outfit headings, Geist Mono code, and a teal brand. Do not substitute Radix or Lucide APIs from memory.
- Use sidebar-01's single panel with grouped navigation. The user rejected the double-sidebar layout: do not reintroduce nested sidebars or a second icon rail. Desktop width is 224px; mobile uses one 256px sheet with the same categories and keyboard access.
- Keep marketing routes (`/`, `/blog/`, `/privacy/`) separate from the compact workspace at `/dashboard/`. Marketing uses documented display typography and the warm surface token; dashboard controls and cards retain compact dimensions.
- Marketing links use `prefetch={false}` to avoid downloading tool bundles before intent and Safari errors when background route requests are interrupted. Preserve client navigation and use responsive static image sources for the exported site.
- Use the confirmed canonical origin `https://keepsimp.vercel.app`, overridable through `NEXT_PUBLIC_SITE_URL`. Include only public pages and completed tool routes in the sitemap. Vercel previews must remain noindex. Keep metadata, visible content, JSON-LD and tool availability consistent.
- Each kind of tool has a colour token (`category-video`, `-audio`, `-image`, `-document`, `-developer`) and each tool an icon of its own in `components/tool-icon.tsx`; give a new tool both. Category colours are for icons, category labels and card hover only, never for text on a tinted fill, buttons or states. Search lives once, in the header (`components/tool-search.tsx`, ⌘K / Ctrl+K); do not add a second search field to the dashboard.
- The articles at `/blog/` are called the blog, never the journal. Every tool that is ready has at least one article (`lib/blog.ts`, `lib/tool-blog.ts`, `lib/json-blog.ts`), and `lib/blog.test.ts` checks that, along with every link inside an article. An article has a heading in the site's voice (`title`), the question people type as its page title (`searchTitle`), and its topics (`keywords`). Write them in plain words, say only what the tools really do, and add a card to `scripts/social-images.mjs` for each new one.
- Reuse `components/ui`. Product screens use semantic tokens and named radius utilities. No arbitrary radii, hardcoded colors, copied Airbnb marks, or proprietary Cereal fonts.
- Reuse the outlined KeepSimp logo assets in `public/brand/` and the matching favicon. Preserve their proportions and geometry; use the light-wordmark variant on dark surfaces. Brand export colors are documented in `docs/design-system.md`.
- Edit `design-system/tokens.json`, then run `npm run design:generate`. Never hand-edit `app/design-tokens.css`. Update the reference and relevant browser assertions when intentionally changing the system.
- Use the compact density: 36px desktop controls and navigation rows, at least 44px on mobile. Label fields, keep focus visible, support reduced motion and both themes, and use honest loading/error/empty states. Planned tools must not appear functional.
- Put pure tool logic in `lib/` or its tool module, with meaningful unit tests covering edge cases. Browser tests should verify real journeys and actual outputs when engines arrive; do not substitute mocked processing for end-to-end validation.
- Before changing JSON workflows, read `docs/json-workspace.md`. Preserve exact numeric tokens, local worker execution, bounded output/patch expansion, explicit previews and source/context-scoped results. Query/schema operations must not fetch references or execute pasted JavaScript.
- Before changing the PDF merger or the PDF splitter, read `docs/pdf-merger.md` and `docs/pdf-splitter.md`; the splitter writes each part with the merger's engine, so a change to one is a change to both. Only files named `mupdf-*.ts` (`lib/pdf-merger/mupdf-engine.ts`, `lib/pdf-reader/mupdf-read.ts`, `lib/pdf-splitter/mupdf-split.ts`) may import `mupdf`, and only its types; they are handed the engine or opened files, so the same code runs in the worker and in Node. The reader (`components/pdf-reader/`, `docs/pdf-reader.md`) is shared by every PDF tool: it draws pages, text and search through the one worker and never opens a file a second time. Pages are copied as whole objects after being made to stand alone, never with `graftPage`, which drops links, notes and fields. Check results with other software (pdf.js, pdf-lib), never with the engine alone, and keep the worker's message handler ahead of the engine import. Files are written with `garbage: 2` after `shareDuplicates` has stored identical parts once; do not go back to `garbage: 4`, which compares every object with every other and takes minutes on a long tagged file. Never call `resolve()` on an engine object: a stream that is held that way is written without its data.
- Before changing the PDF compressor, read `docs/pdf-compressor.md`. It changes a file in place and never turns a page into a picture. A picture is only swapped for a smaller one that has been read back out of the file and checked (pixel for pixel when nothing may be lost); pictures it is not sure of are left as they are; a JPEG is not saved twice at the same size. Level numbers are set by looking at results as well as by measuring: mean SSIM alone lets skies turn into bands. Only lossless JBIG2 is written (`lib/pdf-compressor/jbig2.ts`); do not add the kind that shares shapes between letters. Pictures are encoded on helper workers (`codec.worker.ts`, started by the page one after another and joined to the PDF worker by a port each); everything must still work with none, which is what a device with two cores gets. After changing what is done to pictures or streams, run `npm run pdf:benchmark` on the files listed in the docs and update the published table: it is where the engine's faults with real files were found.
- Before changing the PDF editor, read `docs/pdf-editor.md`. The document in the worker is the truth: every change is one step (`inStep`) and the page is drawn again from the file, so never keep a second model of the document on the page. A change is undone by making the working copy anew from the file as it came and the steps still in force (`madeAgain`); never call the engine's `undo()` or `redo()`, which leave it pointing at fonts and pictures that are gone, and check with `danglingRefs` in any test that undoes something. Changes to a signed file are written after it from such a fresh copy (`lib/pdf-editor/mupdf-signed.ts`), never by saving the working copy with `incremental`. Only the `mupdf-*.ts` files of `lib/pdf-editor/` touch the engine. A form's fields are the file's own (`lib/pdf-editor/forms.ts`): the engine writes their looks, except a list's, which it leaves blank and we draw; a file's scripts are read as text at most and never run. Never save the working copy with `garbage` (later steps name comments and fields by their numbers) and never keep a page object across a change. What is added is a Stamp annotation with our own appearance, set last with no `update()` after it, and is drawn into the page on download unless "Keep editable" is on. Everything read from a file or sent by the page goes through `readObject`. Comments (`lib/pdf-editor/comments.ts`, `mupdf-comments.ts`) are the PDF's own kinds of note, given their look by the engine; only the kinds the editor makes are ever given a new look, and annotations are taken off a page one at a time from a fresh list. Say only what a tool does: "Cover" hides and never removes. There is one PDF editor in the list of tools. A page that opens it for one job (the annotator, Sign PDF, Fill PDF form; later redaction) is a door: a catalogue entry with `partOf`, with its own address, title, help and article, shown focused on that job's tools with the rest one press away, and never a second card, sidebar count or app shortcut. A signature made here is a mark on the page and must never be described as a certificate or as proof of who signed; it is remembered on the device only when the switch is turned on, which starts off every time. A window opened from the editor is rendered inside the reader's own tree (a toolbar or panel slot), never beside it, or screen readers cannot reach it. The words a file already has are changed in `lib/pdf-editor/mupdf-text.ts`: the old letters are taken out of the page's content and the new ones written with the very font object the line was written with, by the numbers that font knows its letters by (learnt from a second copy of the file that is only read); never copy or re-embed a file's font, never take a shape that stands for several letters for its first, and keep the reading-back after every change, which refuses a change that would touch another line. Never run a page's content on the working copy outside an operation: the engine mends a faulty tagged file as it reads, and outside one it leaves a file that cannot be written (`read` opens its own). A font of one's own (`lib/pdf-editor/own-font.ts`) is read on the device, goes by a key made from its bytes, and is never embedded when its maker restricts it; one font is taken out of a collection as a file of its own, and no bold or italic is made from it. Nothing of a file is kept on the device unless a switch is turned on: a draft (`lib/pdf-editor/draft.ts`, `draft-store.ts`) is the file as it came and the list of steps, kept in IndexedDB as bytes, read back through the same checks as a change from the page, and listed on the privacy page with everything else the editor can keep. The editor ships in phases (the list is in the doc); each is tested, pushed to `main` and checked live before the next.
- The site installs as an app and works offline; read `docs/pwa.md` before changing `app/manifest.ts`, `app/sw.js/route.ts`, `lib/pwa.ts`, `lib/offline.ts` or `service-worker/`. `next build` writes `/sw.js` through a static route; do not move that to a step after the build, because the host does not publish files added to `out/` later. The files in `service-worker/` stay plain JavaScript without imports, since their text is copied into the worker. Keep large media such as videos out of the offline copy through `service-worker/rules.js`, register the worker only from the workspace, and cover offline behaviour in `e2e/offline.spec.ts` with the server really stopped.
- Before delivery, run `npm run check`, `npm run test:e2e`, and inspect desktop/mobile UI. Run `npm run build` before standalone browser tests. CI runs all five browser/device profiles. Keep generated reports out of Git.
- Adding new shadcn components can restore default styles. Review their geometry and rerun design/browser checks before using them. Registry-internal geometry in `components/ui` is exempt from the product style scanner; it still requires review against the reference.

Research statements in the design reference must retain source links and distinguish Airbnb's public principles from KeepSimp's own numerical decisions. Phase one is a tested foundation. The marketing phase adds four working tools; the remaining catalogue entries must stay marked as coming soon.
